# 設計方針の決定

- 対象 Issue: #1
- 前提: 10 時間・1 人(AI 支援あり)、Next.js(TypeScript)+ PostgreSQL(Docker)。要件は `docs/requirements.md` を参照。

## 1. 決定事項の一覧

| 項目 | 決定 |
|---|---|
| ORM | Prisma |
| 認証 | 自前の簡易セッション認証(Cookie + DB のセッション、パスワードは bcrypt でハッシュ化) |
| 認可 | サーバ側(Server Action / Route Handler)で必ず検査する |
| 画面の更新方式 | App Router のサーバ側生成(Server Component + Server Action) |
| テスト | Vitest による単体テスト(ロジックのみ)。権限検査と画面は手動確認 |

## 2. ORM: Prisma

- **理由**: 型安全で、スキーマ定義とマイグレーションが一体になっており、DB スキーマ(Issue #3)とユーザ初期登録(Issue #4)の工数を抑えられる。
- **却下した案**: 生の SQL(型安全性とマイグレーション管理を自前で用意する必要がある)。

## 3. 認証: 自前の簡易セッション認証

- ユーザは事前登録制で、ID・パスワードのみの簡易認証でよい(要件書 3 章)。
- パスワードは bcrypt でハッシュ化して保存する。
- ログイン成功時にセッションを DB に保存し、ID を HttpOnly の Cookie で渡す。
- **理由**: Auth.js などは、OAuth やプロバイダ設定を含み、今回の要件に対して設定が過剰になりやすい。
- **却下した案**: Auth.js。ライブラリ利用の学習にはなるが、10 時間の枠では手間が大きい。
- 認証情報や秘密値は環境変数(Git 管理外の `.env`)で渡す。

## 4. 認可

- 権限の検査は、画面の非表示に頼らず、サーバ側の処理で必ず行う。
- 検査する内容: 一般ユーザは自分の回答だけを編集できる。管理者専用の操作(イベント作成、日程確定)は管理者のみ。

## 5. 画面の更新方式

- 回答入力に、その場で画面を更新する動的な操作は求められていない。
- サーバ側でページを生成し、更新は Server Action(フォーム送信)で行う。

## 6. テスト方針

### 自動テスト(Vitest)

DB と Next.js に依存しない**純粋関数**に切り出したロジックだけを対象とする。

| 対象 | Issue | 内容 |
|---|---|---|
| 最適日の判定 | #10 | 必須参加者全員が ○ または △ の日を優先 / × の必須参加者がいる日は優先条件を満たさない / 人数は ○=1、△=0.5、×=0 / 優先条件を満たす日がなければ人数最大の日 / 同点はすべて返す / 必須参加者がいなくても動く |
| 未回答者の抽出 | #9 | 全候補日に未入力のユーザだけを返す / 一部の候補日だけ回答済みの人は含めない / 必須と任意を区別して返す |
| 回答の受付可否 | #8 | 期限前は可、期限後は不可 |

### 手動確認

- **権限検査**(他人の回答を編集できないこと、管理者専用操作を一般ユーザができないこと): DB と認証の結合が必要で、自動化の工数が大きいため、手動で確認する。確認は Issue #11 で実施する。
- 画面の動作と全体の起動: `docker compose up` で起動して確認する。

### 対象外

- 画面の E2E テスト、DB を使った結合テスト(10 時間の枠では、設定と保守の手間が大きいため)。
